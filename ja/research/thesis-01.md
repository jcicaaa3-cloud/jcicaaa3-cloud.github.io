## 1. ロボット評価研究からマルウェアへ {#from-robot}

1学期はロボットの行動評価を研究していました。OpenVLA-OFTをLIBERO-Spatial環境で80回動かし、つかむ・置くといったイベント874件を成功か失敗か判定する基準を比べました。判定基準と正解ラベルを変えると、同じ記録でF1が0.9111から0.5970まで下がりました。モデルはそのままで、評価のしかたを変えただけでここまで数字が動きました。

この研究をまとめる中で評価と検証を扱う力をつけ、卒業論文は中学生のころから関心を持ってきたマルウェアの分野で続けることにしました。ランサムウェア検知の論文を読んでも、まず確かめたかったのはロボット研究のときと同じことでした。検知率98%が、どんなサンプルでテストして出た数字なのかです。

## 2. 先にサンプルを開いてみました {#samples-first}

テーマを決める前に、実際のランサムウェアをいくつか開いてみました。検知モデルが何を見逃すのかを言うなら、見逃したファイルの中身を自分で見られないといけないと思ったからです。

- **Calipso**：11月5日に公開レポートをまとめ、6日からGhidraで静的解析しました。XChaCha20でファイルの先頭5MBだけを暗号化し、ローカルのNTFSドライブはMFTを直接列挙してファイルを探す作りでした。[解析v2.0]({{ '/ja/research/calipso-v2/' | relative_url }})にまとめています。
- **HYFLOCK**：11月8日に[次の解析対象]({{ '/ja/research/hyflock-preview/' | relative_url }})に決め、11月12日に[ハッシュとエンジン別の検知結果]({{ '/ja/research/hyflock-01/' | relative_url }})を書きました。VirusTotalの67エンジン中28が検知しましたが、ランサムウェアの名前を付けたエンジン同士でもKillav、Nishi、Qilinと名前が分かれました。

HYFLOCKの検知名が分かれたことは、後で論文4章の限界に入りました。検知データセットのファミリーラベルも、結局はこうした検知名をもとに付けられるからです。同じ系統が別の名前に分かれていれば、ファミリーで分けて評価しても完全には分かれません。

Calipsoは選定基準と関係なく先に見たサンプルなので、最終原稿の本文からは外しました。

## 3. MLRanと公開分割 {#mlran}

データにはMLRanを選びました。2026年にJournal of Network and Computer Applicationsに掲載された公開の行動データセットで、コードとデータがどちらも公開されているので、自分で動かし直せます。

| 項目 | 内容 |
| --- | --- |
| サンプル | 4,880件（ランサムウェア2,330、正規ソフトウェア2,550） |
| ランサムウェアのファミリー | 64（暗号化型32、モダン15、RaaS 13、ロッカー4）、ファミリーあたり5〜134件、中央値28 |
| 期間 | 2006〜2024年（ランサムウェアは2008〜2024年） |
| 実行環境 | Cuckoo Sandbox 2.0.7、Windows 7ゲスト、1サンプル120秒 |
| 特徴 | 生特徴6,467,926 → 相互情報量で24,162 → RFEで483、すべて0/1 |
| 483個のカテゴリ別内訳 | STR 223、REG 90、API 63、SYS 38、DROP 23、SIG 20、FILE 16、DIR 10、NET 0 |
| 元研究の分割 | サンプル種別ごとにVirusTotal初回提出日順で80:20、学習3,905／テスト975 |
| 元研究の正解率 | LR 98.15%（5モデル中最高）、LightGBM 94.05% |

ファミリーごとの件数、カテゴリ別の特徴数、分割の大きさは、公開リポジトリのメタデータと分割ファイルから自分で数えた値です。正解率は元論文arXiv版の表6からとりました。実験にはGitHubリポジトリのコミット`273fcac`とZenodoレコード23403681のファイルを手を加えずに使いました。

元研究の分割はこうです。サンプルを種別ごとに分け、各種別の中でVirusTotalに初めて提出された日付順に並べ、古い80%を学習に、新しい20%をテストに入れています。種別の中では時間順が守られます。ただ、種別ごとに境界の日付が違いうるので、ある種別の学習サンプルが別の種別のテストサンプルより新しいことはあります。

元論文はファミリー単位で分けた評価をしておらず、未知のファミリーへの汎化を限界として挙げています。

## 4. 分割ファイルを数えてみると {#overlap}

公開されている分割ファイルを開いて、テストセットのランサムウェアがどのファミリーかを数えました。

| | 件数 |
| --- | --- |
| テストセットのランサムウェア | 465 |
| そのうち同じファミリーが学習セットにもあるもの | 451（97.0%） |
| テストセットにしかないファミリー | Akiraの1つ（14件） |

テストのランサムウェア100件のうち97件は、学習で見たファミリーの別サンプルでした。98%という検知率は、ほとんどが「知っているファミリーの新しいサンプル」を当てた結果だということです。学習になかったファミリーをどれだけ捕まえられるかは、この分割ではわかりません。

実際にはどちらも起きます。既知ファミリーの亜種も来るし、初めて見るファミリーも来ます。だから二つの条件の性能は分けて見るべきだと考え、この数字が論文の出発点になりました。

## 5. すでにある研究 {#prior}

評価のしかたが結果をよく見せてしまうという指摘は、すでに何度も出ています。

- Pendleburyら（TESSERACT、USENIX Security 2019）は、時間順を守らない分割と現実と違うクラス比率がマルウェア分類の性能を水増しすることを示しました。
- Arpら（USENIX Security 2022）は、セキュリティ分野の機械学習によくある落とし穴としてデータスヌーピング、標本の偏り、見せかけの相関を挙げました。
- JuとKim（IEEE Access 2025）は、I/Oの順序を変えたランサムウェアが既存の振る舞いベース検知をすり抜けうることを示しました。

調べている途中で、MLRanをファミリー基準で評価し直した論文も見つけました。Nti（Future Internet 2026）はMLRanの483特徴で階層型スパースニューラルネットワークを提案し、層化、時間順、ファミリー分離、オープンセットの4種類の分割を比べていて、比較モデルにLRも入っています。自分がやろうとしていたことと重なる部分があったので、違いを整理しました。

- Ntiのファミリー分離は、サンプルが10件以上あるファミリーだけを60:20:20で分けた1回の分割です。私は64ファミリーすべてを入れた5分割交差検証をしました。
- Ntiは詳しい誤り分析や信頼区間・仮説検定はしていないと書いています。私は見逃したサンプルをSHAPとリバースエンジニアリングで追い、対応のある比較に検定を付けました。

そのため、論文の序論に「MLRanにファミリー分離評価を適用したこと自体は本論文が初めてではない」と書きました。新しいのは誤り分析と統計検定の部分です。

説明の側も似ていました。MLRanの元論文はSHAPとLIMEで主な指標を示し、誤分類された例のいくつかにLIMEを当てていますが、当たったサンプルと見逃したサンプルの寄与を集団として比べてはいません。新しい検知器を作るより、既存のベースラインがどこで、なぜ間違えるのかを見る方向に決めました。

## 6. 研究課題と仮説 {#rq}

| | 問い |
| --- | --- |
| RQ1 | MLRanのベースライン2つをファミリー分離の条件で評価すると、時間順分割と比べてランサムウェアの再現率はどれだけ変わるか |
| RQ2 | ファミリー分離の条件で、真陽性（TP）と偽陰性（FN）のあいだでSHAPの寄与は特徴カテゴリごとにどう違うか |
| RQ3 | 検知に失敗した例を静的リバースエンジニアリングで調べると、特徴の表現とバイナリの機能のあいだで何が一致し、何がずれるか |

仮説は2つ立てました。

- **H1**：ファミリーを分けると、ランサムウェアの再現率は時間順分割より下がり、その低下は一部のファミリーに集中する。
- **H2**：FNでは、文字列（STR）とレジストリ（REG）カテゴリの符号付き寄与の合計が、TPよりランサムウェア側に傾いていない。

H2は最初FILE・DIRカテゴリで立てて、後で変えました。483特徴のうちFILEとDIRは合わせて26個（5.4%）しかなく、STRとREGは313個（64.8%）でした。最初の仮説の結果も論文に載せています。事前登録した仮説ではないので、RQ2の検定は探索的分析として示しました。詳しくは[第2回]({{ '/ja/research/thesis-02/' | relative_url }})に書いています。

ベースラインはLRとLightGBMの2つです。LRは元研究で正解率が最も高く、LightGBMは5モデル中で2番目に低かったものの、木モデルなのでTreeSHAPでSHAP値を正確に計算できます。

リバースエンジニアリングする失敗例は、結果を見る前に基準を決めておきました。

1. ファミリー分離の条件で再現率が最も低いファミリーのサンプル
2. 正規である確率が最も高く出たFN
3. カテゴリ別の寄与の割合がTPの平均から最も離れたFN
4. 2023〜2024年の正規ソフトウェアで出たFP 1件（元研究のFP 12件のうち11件がこの時期のサンプル）

実際にはこの基準を一部しか適用できませんでした。どうなったかは[第3回]({{ '/ja/research/thesis-03/' | relative_url }})に書きました。

## 7. 証拠を分けて書くルール {#evidence}

SHAPはモデルがどの特徴を使ったかを教えてくれるだけで、マルウェアが実際に何をしたかは教えてくれません。リバースエンジニアリングで見つけた機能も、バイナリの中にあることまでしかわからず、120秒の実行でその機能が使われたかはわかりません。そこで、論文のすべての所見に出どころの区分を付けました。

| 区分 | 根拠 | 示せること | 示せないこと |
| --- | --- | --- | --- |
| S（静的） | Ghidra、PE構造、バイト確認 | コードやファイル構造にその機能があること | その機能が実行されること |
| D（動的） | MLRanの特徴行列、出典のある実行記録 | ある1回の実行でその記録が残ったこと | どの実行・環境でも起きること、特徴で表されない動作 |
| M（モデル） | SHAPの寄与 | 分類器が使った特徴とその向き | マルウェアが実際にした動作。Dから独立した根拠にならない |
| R（外部報告） | 出典のある第三者のレポート | レポートが示したハッシュの掲載と分析結果 | 自分での再確認、レポートにない細部 |

所見ごとにレベルも付けました。

- **確認**：バイト、コード、特徴値のように直接見た事実
- **解釈**：いくつかの観察と合うが、直接は確かめていない説明
- **仮説**：さらに確認が必要な説明

失敗の原因についての文は、解釈か仮説のレベルを超えないようにしました。

この表は最初からこの形だったわけではありません。初期の原稿には「違う区分の証拠が2つ同じ向きなら主張する」というルールがありました。でもMはDから取り出した特徴の上で計算されるので、2つが同じ向きになるのはほぼ当然です。これを直すときに「MはDから独立した根拠ではない」を表に入れ、証拠の数ではなく所見ごとのレベルを書く形に変えました。Rも後から分けました。Check Pointのレポートの動的分析結果を最初は「D（第三者）」としていましたが、自分で確かめていない内容を自分の観察と同じ欄に置くのは合っていませんでした。

## 8. 全体の手順 {#procedure}

<figure><a href="{{ '/assets/images/thesis-procedure.webp' | relative_url }}"><img src="{{ '/assets/images/thesis-procedure.webp' | relative_url }}" alt="研究の手順：MLRanデータセット、ベースラインモデル、再現の確認、ファミリー分離評価、結果別SHAP、失敗例の選定、静的リバースエンジニアリング、証拠の区分" loading="lazy"></a><figcaption>論文の図1。上の段が再現と再評価（RQ1）、下の段が説明（RQ2、RQ3）です。</figcaption></figure>

1. MLRanの4,880件（交差検証には重複を除いた4,876件）を用意します。
2. LRとLightGBMを公開分割で学習し直します。
3. 公表された正解率との差が±1ポイント以内なら再現できたとみなします。
4. ファミリー分離の5分割交差検証で評価し直し、時間順分割と比べます（RQ1）。
5. TPとFNのSHAPの寄与をカテゴリごとに比べます（RQ2）。
6. 6節の基準で失敗例を選びます。
7. 選んだサンプルを静的にリバースエンジニアリングします（RQ3）。
8. すべての所見にS・D・M・Rの区分とレベルを付けます。

## 9. 解析環境と安全ルール {#safety}

検知の実験はMLRanが公開した特徴ベクトルのCSVだけを使います。マルウェアのファイルは扱わないので、普段使いのPCで動かしました。Windows 11、Python 3.12.10、scikit-learn 1.6.1、LightGBM 4.6.0で、乱数シードは`20261113`です。

サンプルの実物は、VMware Workstation Pro上のWindows 11仮想マシンの中だけで扱いました。

- ネットワークアダプタとUSBコントローラを削除しました。
- 共有フォルダ、クリップボード共有、ドラッグ＆ドロップを無効にしました。
- サンプルを入れる前のスナップショットを残しました。
- 解析スクリプトは、サンプルのSHA-256が指定した値と一致し、WAN Miniportを除く有効なネットワークアダプタとデフォルトルートがないときだけ動くようにしました。
- 作業はPE構造の解析、文字列の抽出、Ghidra 12.2のheadless解析、PowerShellでのバイト読み取りだけです。論文に出てくる2つのサンプルは実行していません。
- 仮想マシンの外にはテキストとCSVの結果だけを持ち出しました。サンプルはSHA-256でだけ指します。

11月6日に、この仮想マシンでCalipsoを一度実行したことがあります（[Calipso（3）]({{ '/ja/research/calipso-03/' | relative_url }})）。その観察は論文の根拠には使っておらず、2.5節にそのことを書いています。
