## 1. 처음 계획: Shodi {#shodi}

[1편]({{ '/research/thesis-01/' | relative_url }})에서 정한 기준 (1)은 "패밀리 분리 조건에서 재현율이 가장 낮은 패밀리의 샘플"입니다. LR에 적용하면 Shodi, LightGBM에 적용하면 MBRLock이 나옵니다.

MBRLock은 LR이 전부 탐지했고 LightGBM의 실패가 0.475라는 한 점수에 몰려 있어서, 샘플 쪽보다 모델 쪽 원인이 커 보였습니다. Shodi는 LR에서 최저이고 LightGBM에서도 FN이 25건 나온 패밀리라 먼저 보기로 했습니다.

호스트 PC에서 우선순위를 매긴 SHA-256 목록 8개를 뽑았습니다. 1~4번이 Shodi였고, 그중 3개는 두 모델이 모두 놓친 샘플, 1개는 비교용으로 탐지된 샘플이었습니다.

뽑는 과정에서 MLRan 기록만으로 미리 본 것이 있습니다. LR이 놓친 Shodi 11개와 잡은 60개의 기록을 비교하니 차이가 컸습니다.

| 특징 | 놓친 Shodi | 잡은 Shodi |
| --- | --- | --- |
| `comctl32.dll` 로드 | 82% | 2% |
| `SetWindowsHookExW` 호출 | 64% | 2% |
| 키보드 레이아웃 레지스트리 읽기 | 100% | 38% |

놓친 쪽의 비율은 정상 소프트웨어와 비슷했습니다. 120초 동안 GUI 프로그램 같은 동작만 기록됐을 수 있다는 생각이 들었고, 정적 분석에서 설치 프로그램이나 드로퍼로 감싼 흔적을 찾으면 확인할 수 있겠다고 계획했습니다.

그런데 이 SHA-256에 맞는 Shodi 실물을 구하지 못했습니다. 위 표는 그래서 논문에 넣지 않았습니다. 바이너리로 확인하지 못한 관찰이고, 같은 패밀리 안에서만 비교한 값이기 때문입니다. 논문에는 "실패한 샘플이 학습 패밀리와 다른 흔적을 보이는지는 학습 패밀리의 샘플을 같은 기준으로 분석해야 답할 수 있다"며 검정하지 않은 가설로 남겼습니다.

## 2. 기준 (2)로 고른 CryptoLocker {#selection}

Shodi가 막히자 RQ3를 다시 짰습니다. RQ1, RQ2와 표는 그대로 두고 2.4절, 3.3절, 4·5장 일부, 초록만 고치기로 했습니다.

처음에는 이 변경을 "샘플 확보 가능성에 따른 사례 선정 변경"이라고 쓰려고 했습니다. 그런데 새로 분석할 CryptoLocker 샘플(`654c4734…`)은 원래 기준 (2) "정상일 확률이 가장 높게 나온 FN"에 해당하는 샘플이었습니다. 그래서 선정을 바꿨다고 쓰지 않고, 기준 (1)의 Shodi는 구하지 못했고 기준 (2)의 샘플을 분석했다고 그대로 적었습니다.

기준 (2)를 LightGBM에 적용하면 랜섬웨어 확률 0.167로 동점인 CryptoLocker 샘플이 2개 나옵니다. 기준에는 동점 처리 규칙이 없었으니 그중 하나를 고른 건 기준 밖의 선택입니다. 논문에 그렇게 적었고, 분석하지 않은 것도 모두 적었습니다.

- 동점인 다른 CryptoLocker 1개
- LR에 기준 (2)를 적용한 샘플
- 기준 (3)과 (4)에 해당하는 사례

결국 데이터셋 안의 실패 사례 분석은 기준을 일부만 적용한 1건입니다.

고른 샘플은 폴드 3에 있었고, LR은 0.641로 탐지했고 LightGBM은 0.167로 놓쳤습니다.

## 3. 분석 키트 {#kit}

키트는 두 단계로 나눴습니다.

**1단계 (호스트 PC)**: MLRan 특징 행렬과 예측 파일에서 대상 샘플의 특징값, 두 모델의 SHAP 값을 뽑습니다. 악성코드 파일은 쓰지 않습니다.

**2단계 (격리 가상 머신)**: 배치 파일 하나로 돌아갑니다.

- 활성 네트워크 어댑터가 하나라도 있으면 실행하지 않고 멈춥니다.
- 샘플의 SHA-256이 지정한 값과 다르면 멈춥니다.
- 샘플을 바이트로 읽기만 합니다. 섹션, 엔트로피, 임포트, 패커 흔적, 키워드 문자열을 정리합니다.
- MLRan 기록에 있던 문자열·API 특징이 실제 바이너리에 있는지 대조합니다(D와 S 비교). CryptoLocker는 고정 483개 중 STR·API 특징 286개가 대상이었습니다.
- Ghidra 12.2 headless로 자동 분석하고, 파일 탐색과 암호화 관련 API의 호출 위치를 뽑습니다.

키트는 쓰기 전에 자체 테스트(Python 11개, Java 37개 검사)를 돌렸고, 호스트 단계에서 쓰는 예측 파일이 2편 실험의 파일과 바이트 단위로 같은지도 확인했습니다.

처음 Ghidra를 돌렸을 때 자동 분석은 27초 만에 끝났는데, 디컴파일 스크립트가 컴파일 단계에서 실패했습니다. `currentProgram.getEntryPoint()`라는, Ghidra의 `Program`에 없는 메서드를 불렀기 때문입니다. 진입점은 심볼 테이블의 외부 진입점 목록에서 가져와야 합니다. 그 뒤로 보고 싶은 함수를 자동으로 뽑도록 패치해서, Ghidra에서 함수를 하나씩 찾아다니지 않아도 되게 했습니다.

## 4. CryptoLocker: 모델과 기록 {#cl-model}

| 항목 | 값 |
| --- | --- |
| SHA-256 | `654c473412c0e3f812c94d25f785c3173e2d8bda08701efdc7a937e55a27d692` |
| 아키텍처 | x86 |
| 섹션 | 5개 |
| 파일 엔트로피 | 6.68 (섹션 최대 6.65) |
| 임포트 함수 | 129개, CryptoAPI 임포트 없음 |
| LR | 0.641, 탐지 |
| LightGBM | 0.167, FN |

**모델(M)**: LightGBM 점수를 가장 크게 낮춘 특징은 `ole32.dll` 로드였습니다. SHAP −1.13으로, 이 샘플의 음의 기여 합 중 67%를 차지했습니다. 2위 특징이 +0.13이니 이 특징 하나가 판정을 정상 쪽으로 끌고 갔습니다. [2편]({{ '/research/thesis-02/#top-features' | relative_url }})에서 본, 정상 소프트웨어의 91%에 있는 그 특징입니다.

**기록(D)**: 이 샘플에서 값이 1인 특징은 REG 9개, SYS 5개, FILE 1개, 모두 15개였습니다. 대부분 창과 입력기 초기화에 해당하는 흔적이었습니다. 분석에 쓴 483개 선택 특징 안에서 `NtWriteFile` 특징, 디렉터리 범주, 드롭 파일 범주는 모두 0이었습니다.

0이라는 건 해당 특징으로 표현된 기록이 없었다는 뜻입니다. 원본 Cuckoo 로그의 API 호출 순서와 인자는 근거로 쓰지 않았으므로, 실행 전체에서 파일 쓰기나 디렉터리 열거가 없었다고는 할 수 없습니다.

## 5. CryptoLocker: 바이너리 {#cl-binary}

Ghidra로 따라간 흐름입니다(S).

```text
창 제목 "CryptoLocker Decryption Software"
 └ 확인 창 "Do you want to decrypt PC?"  → '예'
    └ FUN_00415500   처리 스레드 생성
       └ FUN_004139e0   드라이브 열거 (A: 제외, 이동식·고정·네트워크·RAM 디스크)
          └ FUN_00414b30   폴더 재귀 탐색
             └ FUN_004135b0   파일마다 처리
FUN_004152a0
 ├ FUN_004140f0   파일을 CREATE_ALWAYS로 엶
 └ 메시지 "Files are now decrypted. Your PC will be restarted."
```

그 밖에 이런 함수가 있었습니다.

- `FUN_00413140`: `MoveFileExW`로 파일 이름을 두 가지 방식 중 하나로 바꿉니다.
- `FUN_00414a30`: `DeleteFileW`를 부릅니다.
- `FUN_00412f70`: 폴더 경로와 `DECRYPT_INSTRUCTIONS.html` 경로를 만듭니다.

복호화 화면을 띄우고 '예'를 눌러야 파일 처리 스레드가 시작되는 구조입니다. 드라이브를 돌고 폴더를 재귀로 따라가는 부분까지는 확인했습니다. 열거한 파일을 암호화하는지 복호화하는지, `FUN_004140f0`이 `CREATE_ALWAYS`로 여는 파일이 무엇인지는 정하지 못했습니다. 드라이브 순회, 재귀 탐색, 이름 변경은 암호화 프로그램에도 똑같이 있는 구조라 이것만으로는 가를 수 없습니다.

D와 S가 어긋난 곳도 있었습니다. `FindResourceExW`, `LoadResource`, `DrawTextExW`는 MLRan 실행 기록에는 있는데 이 파일의 임포트에는 없었습니다. 샘플이 직접 부른 게 아니라 창을 그리는 시스템 DLL이 대신 부른 호출까지 Cuckoo가 기록했을 수 있습니다. 그렇다면 행위 특징에는 프로그램 자체의 동작이 아닌 것도 섞입니다.

## 6. 디펜더는 왜 랜섬웨어로 지웠나 {#defender}

분석하는 동안 Microsoft Defender가 이 파일을 랜섬웨어로 잡아 지웠습니다. "복호화 화면이면 레이블이 잘못된 건가" 하는 생각이 들었는데, 그렇게 볼 근거는 못 됩니다.

백신은 파일이 무슨 동작을 하는지보다 어느 랜섬웨어 패밀리의 구성품인지로 판정하는 경우가 많습니다. 복호화 도구도 공격자가 만들어 피해자에게 주는 패키지의 일부이니 같은 패밀리 이름으로 잡히는 게 자연스럽습니다. 2013~2014년의 원조 CryptoLocker도 한 프로그램이 파일을 암호화하고, 돈을 내면 같은 화면에서 복호화까지 하는 구조로 알려져 있습니다.

그래서 이 사례에서 따질 건 레이블이 아니라 기록된 행위입니다. MLRan이 이 파일을 CryptoLocker로 붙인 건 맞을 수 있습니다. 문제는 탐지 모델이 보는 건 120초 동안의 행위라는 점입니다.

## 7. CryptoLocker에서 말할 수 있는 것 {#cl-claim}

| 소견 | 구분 | 수준 |
| --- | --- | --- |
| LightGBM 점수를 가장 크게 낮춘 특징은 `ole32.dll` 로드 (SHAP −1.13, 음의 기여 합의 67%) | M | 확인 |
| 값이 1인 REG·SYS·FILE 특징 15개는 대부분 창·입력기 초기화와 관련 | D | 확인 |
| 483개 선택 특징에서 `NtWriteFile`, DIR, DROP 특징은 모두 0 | D | 확인(특징 범위) |
| 복호화 화면의 확인 창에서 '예'를 고르면 처리 스레드 생성 (`FUN_00415500`) | S | 확인 |
| 처리 스레드가 드라이브 열거로 이어짐. 파일 내용을 바꾸는 방식은 미확인 | S | 확인 / 미확인 |
| 120초 동안 확인 창 이후 단계에 이르지 않았을 가능성 | S·D | 가설 |

이 관찰들을 이어 보면 하나의 해석이 나옵니다. 샘플이 120초 동안 확인 창에서 멈춰 파일 처리 단계에 가지 못했고, 그래서 기록이 평범한 GUI 프로그램처럼 남았고, LightGBM은 그 기록을 정상으로 판단했다는 해석입니다.

하지만 논문에서는 이걸 가설로 적었습니다. 실행 화면이나 원본 로그로 확인 창에서 기다렸는지 보지 않았습니다. 그리고 M은 D에서 뽑은 특징 위에서 계산되니 둘이 같은 방향이라는 게 독립된 두 증거가 되지 않습니다. 복호화 화면이 있다는 것만으로 이 파일을 복호화 도구나 정상 소프트웨어로 볼 수도 없습니다.

지금 증거로 말할 수 있는 건 이 샘플의 패밀리 레이블과 MLRan에 기록된 행위 표현 사이에 어긋남이 있을 수 있다는 정도입니다. 레이블이 틀렸다는 결론은 내릴 수 없습니다. 가장 낮은 점수의 FN부터 고르는 기준 (2)가 이런 샘플을 먼저 드러낼 수 있다는 점은 논문 4장에 적었습니다.

## 8. HYFLOCK: Go 로더 {#hy-loader}

HYFLOCK 캐리어는 비공개 경로로 구한 파일이고, 데이터셋 밖의 사례입니다. 해시와 엔진별 탐지 결과는 [HYFLOCK (1)]({{ '/research/hyflock-01/' | relative_url }})에 있습니다.

| 항목 | 값 |
| --- | --- |
| SHA-256 | `b15482d0846ef997f9c049e77d85efeba4ab9b33550b4384052efeb1a3dcc8cc` |
| 크기 | 3,851,808 bytes |
| 아키텍처 | x64 |
| 섹션 | 6개, 파일 엔트로피 6.37, 섹션 최대 6.16 |
| 임포트 함수 | 39개 |

섹션 최대 엔트로피가 6.16이라 암호화된 페이로드를 섹션 안에 품고 있는 모양은 아니었습니다. 그래서 페이로드가 어디 붙어 있는지부터 찾았습니다.

Ghidra에서 본 것입니다.

- Go 소스 경로 `/tmp/hyflock-loader-689098328/stub.go`가 남아 있었습니다. 빌드한 쪽이 `hyflock-loader`라는 이름을 썼다는 흔적인데, 문자열은 조작할 수 있으니 패밀리를 정하는 근거로는 쓰지 않았습니다.
- `main.main`은 `main.findPayload`가 실패하면 메시지를 출력하고 끝나고, 성공하면 `main.dropAndExec`로 넘어갑니다. 파일 끝에 붙은 페이로드를 찾아 임시 파일로 써서 실행하는 로더 구조입니다.

## 9. HYFLOCK: 끝 16바이트 {#hy-footer}

`main.findPayload`가 파일 끝에서 페이로드를 찾는다면 파일 끝에 그 형식이 실제로 있어야 합니다. 가상 머신 안에서 PowerShell로 마지막 16바이트를 읽었습니다.

```text
===== HYFLOCK FINAL CHECK =====
Tail HEX          : 4859464C434B30330000000000224A10
Magic             : HYFLCK03
Magic valid       : True
Payload size      : 2247184
Payload offset    : 1604608
Overlay size      : 2247200
Within overlay    : True
Exact size match  : True
```

앞 8바이트는 ASCII `HYFLCK03`이고, 뒤 8바이트는 빅엔디언 `0x224A10` = 2,247,184입니다. 숫자를 맞춰 보면 이렇습니다.

```text
2,247,184 (페이로드) + 16 (푸터)        = 2,247,200 = 캐리어 마지막 섹션 뒤 오버레이 크기
3,851,808 − 16 − 2,247,184              = 1,604,608 = 페이로드 시작 위치 = 마지막 섹션 원시 데이터 끝
```

실제 파일 끝에 로더가 읽는 형식 그대로 데이터가 붙어 있다는 것을 바이트로 확인했습니다.

그다음 페이로드 시작 위치의 첫 2바이트를 읽었습니다.

```text
HEX: 4D-5A
MZ 발견!
```

부착된 데이터는 `MZ`로 시작하고 PE 서명이 있었으며, Rust 흔적이 보였습니다.

<figure><a href="{{ '/assets/images/hyflock-layout.svg' | relative_url }}"><img src="{{ '/assets/images/hyflock-layout.svg' | relative_url }}" alt="HYFLOCK 캐리어의 바이트 배치: Go 로더 1,604,608바이트, 내장 PE 2,222,592바이트, 남는 24,592바이트, 푸터 16바이트" loading="lazy"></a><figcaption>HYFLOCK 캐리어의 바이트 배치. 마지막 두 칸은 실제 비율보다 크게 그렸습니다.</figcaption></figure>

내장 PE의 섹션 테이블로 끝을 계산하면 페이로드 시작에서 2,222,592바이트 지점입니다. 페이로드 길이는 2,247,184이니 PE 섹션 끝 뒤로 24,592바이트가 더 있습니다. PowerShell 출력의 "Bytes after estimated PE end: 24608"은 푸터 16바이트까지 포함한 값입니다.

## 10. 보고서 해시와 맞지 않았던 것 {#hy-hash}

처음에는 Check Point 블로그 글에 해시가 없어서 이 샘플이 어느 빌드인지 확인하지 못했다고 원고에 적었습니다. 나중에 블로그가 링크한 PDF 보고서 부록을 보니 18쪽 IOC 표에 해시가 다 있었습니다. 제 샘플의 SHA-256은 거기서 "October Go carrier"로 나옵니다. 원고의 그 문장은 지우고 등재 사실로 바꿨습니다.

보고서 9쪽은 Go 캐리어가 Rust 랜섬웨어 PE와 16바이트 `HYFLCK03` 푸터를 담고, 페이로드를 임시 실행 파일로 써서 실행한다고 설명합니다. 제가 바이트로 본 구조와 같습니다. 푸터 안의 필드 구성(마커 8바이트 + 길이 8바이트)은 보고서에 나오지 않고 제가 확인한 것입니다.

맞지 않은 것도 있었습니다. 보고서는 내부 페이로드로 "October exact child"와, 푸터 16바이트를 남긴 분석용 산출물 "Footer-retaining artifact"의 두 해시를 실었습니다. 저는 PE 섹션 끝까지인 2,222,592바이트 영역만 잘라 해시를 구했고, 이 해시는 두 해시 모두와 달랐습니다.

보고서는 두 파일의 크기나 캐리어 안 범위를 밝히지 않았습니다. 제가 자른 범위가 보고서의 어느 파일과 같은 범위라고 볼 근거가 없으니, 해시가 다르다는 건 보고서와의 불일치를 뜻하지 않습니다. 보고서가 설정이 파일 끝을 기준으로 놓인다고 적었으니 남는 24,592바이트가 설정일 수 있다는 추측은 해 볼 수 있습니다. 페이로드를 오프셋 1,604,608부터 정확히 2,247,184바이트만 잘라 해시를 대조하는 일은 아직 하지 않았습니다.

암호화 쪽은 제가 확인한 게 없습니다. 바이너리에서 찾은 `BCryptGenRandom`은 Rust 표준 라이브러리도 쓰는 함수라 근거로 쓰지 않았습니다. AES 카운터 모드, 4,096비트 RSA 공개키, 초기 10월 산출물에서의 암호화 확인은 모두 Check Point의 분석이고, 논문에는 R 구분의 "보고서 소견"으로만 적었습니다.

## 11. HYFLOCK에 모델 점수를 붙이지 않은 이유 {#hy-no-score}

HYFLOCK을 LR이나 LightGBM으로 판정하려면 MLRan과 같은 조건(Cuckoo, Windows 7, 120초)에서 실행해 같은 형식의 특징을 뽑아야 합니다. 이번 논문의 안전 규칙은 샘플을 실행하지 않는 것이고, 이걸 하려면 승인된 샌드박스가 필요합니다.

그래서 HYFLOCK에는 확률도 SHAP도 붙이지 않았고, 정적 분석 소견을 공개 보고서와 대조하는 데만 썼습니다. MLRan 밖의 최신 샘플을 같은 조건에서 실행해 판정하는 일은 이후 연구로 넘겼습니다.

## 12. 원고를 고친 과정 {#revisions}

원고는 v14까지 왔습니다. 분량은 7쪽 제한이 있고, 한국어·영어·일본어본을 같이 맞췄습니다. Calipso 분석과 정상 소프트웨어 범주별 분리 결과는 분량 때문에 본문에서 뺐습니다.

주장의 수위를 고친 곳을 처음 문장과 최종 문장으로 나란히 놓으면 이렇습니다.

| 주제 | 초기 원고 | 최종 원고 |
| --- | --- | --- |
| CryptoLocker | 세 구분의 증거가 같은 방향이니, 이 FN은 기록에 랜섬웨어 행위가 거의 없던 경우로 본다 | M은 D에서 나왔으니 독립된 두 증거가 아니다. 확인 창에서 멈췄다는 건 가설이다 |
| LightGBM 하락 | 패밀리 일반화의 한계보다 임계값 민감도로 본다 | 정한 조건에서 학습에 없던 패밀리를 놓친 건 사실이다. 좁은 출력 범위는 기제 중 하나다 |
| LR 결과 | 특징 선택 때문에 상한일 수 있다 (재선택 전) | 재선택 뒤에도 97%대여서 두 설명과 모두 양립한다. 하락 전체를 누출 효과로 볼 수 없다 |
| 465개 비교 | 패밀리를 분리하면 재현율이 낮아졌다 | 폴드 평균을 본 뒤 추가한 사후 비교다. 차이는 프로토콜 전체가 바뀐 결과다 |
| RQ2 검정 | H2를 지지한다 | 사전 등록하지 않은 탐색적 분석이다. FN의 기여가 작은 건 정의상 예상된다 |
| HYFLOCK | 보고서에 해시가 없어 빌드를 확인하지 못했다 | 부록 18쪽에 같은 SHA-256이 등재되어 있다 |
| HYFLOCK 암호화 | 제3자 동적 증거(D)로 표시 | 재확인하지 않은 보고서 소견(R)으로 따로 표시 |
| 선행 연구 | – | MLRan에 패밀리 분리 평가를 적용한 것 자체는 처음이 아니다 (Nti) |

원고의 숫자는 표로 뽑아서 하나씩 출처를 확인했습니다. 원 논문과 같은 값인지, 산술로 맞는지(예를 들어 451/465 = 97.0%, 465 − 451 = 14 = Akira 14개), 실험 결과 파일로 확인되는지로 나눴습니다. LightGBM의 시간순 혼동행렬처럼 원고에 직접 없는 값은 재현율과 FPR에서 거꾸로 계산해 맞는지 봤습니다.
