Calipso.exe를 Ghidra 12.2로 정적 분석한 정리본입니다. 앞서 쓴 (1)~(3)편 내용을 포함하고, 그 뒤에 본 암호화 구조와 실행 흐름을 더했습니다. 샘플은 11월 6일에 격리 VM에서 한 차례 실행해 확장자 변경과 바탕화면 안내만 확인했습니다([(3)편]({{ '/research/calipso-03/' | relative_url }})). 이 글의 분석은 그 뒤 정적 분석으로만 진행했고, 실행 기록은 Recorded Future Triage 공개 보고서를 참고했습니다. 함수 주소는 이미지 베이스 `0x140000000` 기준입니다.

## 요약

- 파일은 XChaCha20으로 암호화합니다. 파일마다 앞 최대 5MB만 제자리에서 덮어씁니다.
- 실행 한 번에 32바이트 세션 키 하나를 만들고, 바이너리에 들어 있는 RSA-4096 공개키(OAEP, SHA-1)로 암호화해 모든 파일 끝에 붙입니다.
- 암호화된 파일은 원본보다 정확히 536바이트 커집니다(nonce 24B + RSA 암호문 512B).
- 공격자 개인키 없이는 복호화할 수 없습니다. 다만 5MB를 넘는 파일은 뒷부분이 원본 그대로 남고, 세션 키를 메모리에서 지우지 않아서 감염 중에 뜬 메모리 덤프가 있으면 거기서 키를 찾을 수 있습니다.
- 로컬 NTFS 드라이브는 MFT를 직접 열거해서 파일 목록을 만들고(`FSCTL_ENUM_USN_DATA`), 그 밖의 경로는 폴더를 따라 탐색합니다.
- 그 밖에 관리자 권한 재실행 요청, 허용 목록 밖 프로세스 종료, 섀도 복사본·백업 카탈로그 삭제, 부팅 복구 끄기, 이벤트 로그 전체 삭제, 바탕화면 고정, `recovery.txt` 작성을 합니다.

## 분석 대상

| 항목 | 값 |
| --- | --- |
| 파일명 | `Calipso.exe` |
| SHA-256 | `9f77af05e8b3112eb13777853c7397442d8467549c3bce01f2639305f98e96ed` |
| 형식 | Windows x64 PE, 약 7.7MB |
| 빌드 | MinGW-w64 GCC, Crypto++ 정적 링크 (CMake 빌드 경로 `/src/build/_deps/cryptopp-cmake-build/` 잔존) |
| 분석 | Ghidra 12.2, 정적 분석만 |

함수 이름은 남아 있지 않아서(`FUN_`), Windows API를 거꾸로 따라가는 방식으로 분석했습니다. 알고리즘과 처리 단계는 남아 있는 Crypto++ 클래스 이름(RTTI)과 디버그 로그 문자열로 구분했습니다.

## 실행 흐름

본체는 `FUN_14000d810`입니다. 호출 순서대로 정리하면 아래와 같습니다.

```text
FUN_14000d810
 ├ 환경변수 CALIPSO_LOG 확인 → 디버그 로그 켜기/끄기
 ├ 내장 PEM 공개키 → Base64 디코딩 → RSA 공개키 로드
 ├ FUN_1400059f0  SeDebug / SeBackup / SeRestore 권한 켜기
 ├ FUN_140005bb0  허용 목록 밖 프로세스 종료
 ├ 보조 스레드 2개 시작
 ├ FUN_140004ab0  세션 키 32B 생성
 ├ FUN_14000d250  세션 키를 RSA-OAEP로 암호화 → 512B
 ├ 대상 결정: 인자 없으면 전체 볼륨, 있으면 드라이브 문자 또는 UNC 경로
 ├ FUN_1400098d0  파일 탐색 + 다중 스레드 암호화
 ├ 보조 스레드 종료 대기
 ├ FUN_1400055a0  바탕화면에 recovery.txt 작성 후 열기
 └ "[*] Done."
```

관리자로 다시 실행하는 함수(`FUN_140001ef0`, `ShellExecuteW`의 `runas`)와 바탕화면 변경 함수(`FUN_1400066a0`)는 위 흐름과 별도로 들어 있습니다.

## 암호화

### 파일 하나 (`FUN_140006c80`)

1. 파일을 읽기·쓰기, 공유 없음으로 엽니다. 크기가 0이면 건드리지 않습니다.
2. 앞에서부터 최대 `0x500000`(5MiB)만 읽습니다.
3. 파일마다 24바이트 nonce를 새로 만듭니다(Crypto++ 난수 생성기, OS 난수로 시드).
4. 세션 키(32B)와 nonce(24B)로 XChaCha20을 설정하고, 읽은 버퍼를 같은 버퍼에 암호화합니다.
5. 파일 처음으로 돌아가 같은 길이만큼 덮어쓰고, 파일 끝에 nonce와 RSA로 암호화한 세션 키를 붙입니다.
6. `MoveFileExW`로 이름 끝에 `.calipso`를 붙입니다.

```c
if (0x500000 < fileSize) toRead = 0x500000;                 // 앞 5MiB만
FUN_1400145f0(&cipher, sessionKey, 0x20, nonce, 0x18);      // 키 32B, nonce 24B
```

키 32B·nonce 24B에 크기가 안 바뀌는 스트림 암호이고, 바이너리에 `XChaCha20_Policy`, `SymmetricCipherFinal<…XChaCha20_Info>` RTTI가 있습니다. Salsa20 계열 RTTI는 없습니다.

### 암호화된 파일 구조

```text
[ 앞 최대 5MiB: 암호문 ][ 5MiB 이후: 원본 그대로 ][ nonce 24B ][ RSA 암호문 512B ]
```

- 원본보다 정확히 536바이트 커집니다.
- 같은 실행에서 암호화된 파일은 마지막 512바이트가 모두 같습니다. 세션 키를 한 번만 RSA로 암호화해서 모든 파일에 붙이기 때문입니다. 사고 대응 때 같은 감염에서 피해를 본 파일을 묶는 데 쓸 수 있습니다.

### 세션 키와 공개키

- `FUN_140004ab0`: Crypto++ 난수 생성기로 32바이트 세션 키를 만듭니다. 시드는 `CryptGenRandom`에서 받습니다.
- `FUN_14000d250`: 세션 키를 내장 공개키로 암호화합니다. 출력 크기는 모듈러스 크기(512B)입니다. 바이너리 안의 RSA 암호화 클래스는 `RSAES<OAEP<SHA1>>` 하나뿐입니다.
- 공개키는 `0x1402EB9C0`에 PEM(`BEGIN PUBLIC KEY`) 텍스트 800바이트로 들어 있습니다. 본체가 줄 단위로 읽으며 `-----`가 들어간 머리줄과 꼬리줄을 빼고 Base64로 디코딩합니다.

| 항목 | 값 |
| --- | --- |
| 알고리즘 | RSA 4096비트, e = 65537 |
| SPKI(DER) SHA-256 | `3ec19d669d122966b8365722060a32dfbe5f6ca09d12b3397bb6940d831005d2` |

### 복구 가능성

- 세션 키는 RSA-4096 OAEP로 보호돼서 공격자 개인키 없이는 풀 수 없습니다.
- 5MiB를 넘는 파일은 뒷부분이 원본 그대로입니다. 동영상, 데이터베이스, 디스크 이미지처럼 큰 파일은 일부를 살릴 수 있습니다.
- 본체는 세션 키와 RSA 암호문을 0으로 지우지 않고 해제합니다(`FUN_14000d810` 끝부분). 파일 암호화 함수 쪽은 cipher 상태를 지웁니다. 감염 중이나 직후의 메모리 덤프에서 세션 키를 찾으면 그 실행으로 잠긴 파일을 전부 풀 수 있습니다. 키가 실행당 하나이기 때문입니다.

## 파일 탐색 (`FUN_1400098d0`)

### 스레드 구성

| 역할 | 개수 |
| --- | --- |
| 암호화 작업자 | CPU 코어 수 × 2, 최소 8, 최대 64 |
| 폴더 트리 탐색 (MFT를 못 쓸 때) | 2~8 |
| 폴더별 처리 | 2 |

작업자 스레드(`FUN_140007430`)는 공유 대기열에서 경로를 하나씩 꺼내 암호화하고, 성공·실패 개수를 원자적으로 셉니다.

### MFT 열거

볼륨이 `X:` 형식이고, 드라이브 종류가 고정 또는 이동식이고, 파일시스템이 NTFS이면 MFT 경로를 탑니다.

1. `\\.\X:`를 `FILE_FLAG_BACKUP_SEMANTICS`로 엽니다.
2. 64MB 버퍼를 잡고 `DeviceIoControl(0x900B3)`을 반복 호출합니다. `0x900B3`은 `FSCTL_ENUM_USN_DATA`입니다. 입력은 `MFT_ENUM_DATA_V1`(32B)이고, 실패하면 V0(24B)로 다시 시도합니다.
3. 레코드를 해시맵에 모으고(50만 칸 예약), 디렉터리와 리파스 포인트를 뺀 항목을 파일로 셉니다.
4. 부모 참조를 따라 전체 경로를 복원해 암호화 대기열에 넣습니다.

```c
DeviceIoControl(hVolume, 0x900b3, &enumData, 0x20, buf, 0x4000000, &returned, NULL);
```

조건에 맞지 않으면(NTFS가 아니거나 네트워크 경로이거나 MFT 열거가 실패하면) 폴더를 따라 내려가는 일반 탐색으로 넘어갑니다.

(2)편에서 `0x900B3`이 어디에 쓰이는지 모른다고 적었는데, 로컬 NTFS 드라이브의 파일 목록을 한 번에 얻는 용도였습니다. 이 경로를 타면 디버그 로그에 `[+] MFT: …`가 찍힙니다.

탐지 쪽에서 보면, 보통 랜섬웨어는 `FindFirstFileW`/`FindNextFileW`를 폴더마다 반복 호출하는데, MFT 열거는 볼륨당 `DeviceIoControl` 호출 몇 번으로 끝납니다(한 번에 최대 64MB씩 받음). API 호출 빈도로 판단하는 탐지 모델에는 전혀 다른 패턴으로 보입니다.

## 암호화 전 준비

### 권한 (`FUN_1400059f0`)

`SeDebugPrivilege`, `SeBackupPrivilege`, `SeRestorePrivilege`를 켭니다. 다른 프로세스를 종료하고, 접근 권한(ACL)이 막힌 파일까지 읽고 쓰는 데 쓰는 권한입니다.

### 프로세스 종료 (`FUN_140005bb0`)

실행 중인 프로세스를 돌면서, 이름(소문자)에 허용 목록 문자열이 하나도 들어 있지 않으면 `TerminateProcess`로 종료합니다. 목록은 `0x1401ED000`에 72개입니다. 죽일 목록이 아니라 살려둘 목록이라서, Office, DB, 브라우저, 백업 프로그램, 서드파티 백신은 전부 꺼집니다.

| 분류 | 살려두는 프로세스 (일부) |
| --- | --- |
| OS 핵심 | system, smss, csrss, wininit, services, lsass, winlogon, svchost, registry, memory compression |
| 화면·셸 | explorer, dwm, sihost, shellexperiencehost, startmenuexperiencehost, logonui |
| 명령 실행에 필요 | conhost, wmiprvse, dllhost, taskhostw |
| Microsoft Defender | msmpeng, mssecflt, securityhealthservice |
| 가상화 도구 | vboxservice, vboxtray, vmtoolsd, vmwaretray, qemu-ga, vmic* (Hyper-V), vmcompute, hvhost |
| 기타 | powershell, 그래픽 드라이버 트레이 |

부분 문자열 비교라서 이름에 `system` 같은 단어가 들어 있으면 종료를 피합니다.

## 복구 방해와 로그 삭제

`FUN_140002320`이 `cmd.exe /C <명령>`을 창 없이 실행하고 끝날 때까지 기다립니다. `cmd.exe /C ` 문자열은 정수 상수로 조립돼 있어 일반 문자열 검색에는 나오지 않습니다.

| 함수 | 명령 |
| --- | --- |
| `FUN_140005fc0` | `vssadmin Delete Shadows /All /Quiet` |
| | `wmic shadowcopy delete /nointeractive` |
| | `wbadmin delete catalog -quiet` |
| | `bcdedit /set {default} bootstatuspolicy ignoreallfailures` |
| | `bcdedit /set {default} recoveryenabled No` |
| `FUN_140006280` | `for /F "tokens=*" %i in ('wevtutil el') do wevtutil cl "%i"` |

Triage 실행 기록에 나온 `vssadmin`, `wmic`, `wbadmin`, `bcdedit`, `wevtutil` 프로세스와 일치합니다. 마지막 명령은 보안 로그만이 아니라 모든 이벤트 로그 채널을 지웁니다.

## 랜섬노트와 바탕화면

- `FUN_1400055a0`: 바탕화면 폴더에 `recovery.txt`를 쓰고 기본 편집기로 엽니다. 실패하면 `notepad.exe`를 직접 실행합니다. 노트 내용에는 바이너리에 하드코딩된 Case ID가 들어갑니다(`3422…`, 이하 생략).
- `FUN_1400066a0`: 바이너리 안의 PNG(`0x1401ED300`, 1,042,055B)를 파일로 쓰고 바탕화면으로 지정합니다. `HKCU\Control Panel\Desktop`뿐 아니라 `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System`에도 써서 사용자가 바탕화면을 바꾸지 못하게 합니다.
